# How To Hero video

Shorts are made with `pipeline2/` next to this file (canvas renderer + Kokoro or Edge voice + ffmpeg + Chromium; all free, no signups). The old `pipeline/` (HyperFrames) is kept for documentaries and for rebuilding old `videos/vN` ids.

Art is drawn in code only (the style kits draw `scenes.json`). Never use AI image or video generation (Gemini, Imagen, any image model or connector) unless the user asks for it on that video in its `note`.

## Build run: loop, one video at a time

The video jobs are two scheduled tasks. The **scout** (`SCOUT.md`) only proposes news stories and ideas as cards; it builds nothing. The **build run** (this section) builds what the user approved. Its numbers live in `flow.json` next to this file (settings only; the steps are here). Before claiming anything, read `flow.json`: if `build.paused` is true, stop and say the run is paused. Keep track of time: once `build.budgetMinutes` have passed since the run started, finish the video in hand and claim no more.

Ideas and finished videos live in the user's Inbox (Google Sheet + API + Telegram buttons; see the inbox repo's docs/FAQ.md). The old How To Hero artifact queue is retired: never read or write it, even if a task prompt still names it. Call the Inbox only through `inbox.sh` (next to this file) with `INBOX_URL` and `INBOX_TOKEN` set; never print, log or commit the URL, the token or an upload link. If the first Inbox call is refused (for example by a permission check) or fails twice, stop and say so. Once you have claimed an item, if a call fails twice, stop and say which call failed.

Worker id: the letter from the task prompt plus 4 random characters, e.g. `B-7f3k`. Pick it once at the start. Make ONE video at a time and upload it before starting the next, so a usage limit only loses the video in progress.

Card types: `story` = a news card, `idea` = an explainer idea card; both are only a proposal, with nothing built. `video` = a finished video to review. Item lifecycle: `story`/`idea` `pending` (the user approves or rejects on Telegram) → `approved` = ready to build → you claim it, `building` → same item becomes type `video`, `pending`, with the MP4 attached (every file stays in one Drive folder; the status is the only state) → the user approves or rejects with a `note` → the auto-publisher (`publisher/publish.py`, a GitHub Action) posts approved videos once their `slot` has passed (an empty slot counts as due) and marks them `posted`. Never set `data.remind` (no manual posting reminders). Never run `cleanupPosted`: deleting old posted videos is the user's button only.

1. Claim, news first. List free stories: `inbox.sh call '{"action":"list","type":"story","status":"approved,building","claimed":"no","ttlMinutes":<build.claimTtlMinutes>,"limit":1000}'`. Pick lane A (`data.lane` "A", trending) before lane B, oldest first, and claim it: `inbox.sh call '{"action":"claim","id":"<id>","by":"<worker id>","ttlMinutes":<build.claimTtlMinutes>,"set":{"status":"building"}}'`. On `already_claimed`, pick the next one. When no story is free, take the oldest idea in one step: `inbox.sh call '{"action":"claimNext","by":"<worker id>","type":"idea","status":"approved,building","ttlMinutes":<build.claimTtlMinutes>,"set":{"status":"building"}}'`; `"item": null` means nothing is approved: stop. If the claimed idea is a documentary (`series` "DOC", `kind` "doc" or id `doc-...`), keep the claim and don't build it (the claim keeps the next `claimNext` from returning it this run; it expires by itself) and claim again. The claim marks the card `building` and records who holds it before any work starts, so two runs never build the same card. `building` is in the status list so a card a crashed run left behind is picked up again once its claim expires; live claims are skipped.
2. Duplicate check: `dupcheck.py "<title> <data.topic>" --skip <item id>` (next to this file; compares with every Inbox item in every status). If it prints a DUPLICATE, or a CHECK item clearly covers the same subject, release the item with `"set":{"status":"rejected","note":"duplicate of <other id>"}` and go back to step 1. Exit code 2 means the check could not run: treat it like a failed Inbox call.
3. Build. A `story`: follow `NEWS.md` "Build a story". An `idea`: read `title`, `summary`, `note` (the user's feedback, follow it) and `data` (`kind`, `topic`, `angle`, `hook`, `why`, `sources`, `aha`, `series`, `fact`, `maxSeconds`), and follow the build note for its `kind` in `IDEAS.md` "Build notes per kind", build it with "Worker steps" and "Build one video", upload with `inbox.sh up out/<file> <item id>` (from the skill folder; `out/` is ignored by git) (attaches the Drive file and sets `link`), make its platform versions ("Platform versions" below), then hand it to the user: `inbox.sh call '{"action":"release","id":"<id>","by":"<worker id>","set":{"type":"video","status":"pending","title":"<yt title>","summary":"<duration> s, <one-line verification result>","data":{<the old data plus videoRef, yt, ig, pin, versions, links>}}}'`. Every video card's `data`, a story's too, also gets `hookPattern` (the hook's shape: `claim` a bold surprising statement, `number` led by a number, `contrast` "X but Y", or `how` "how X does Y"), `channel` (from `flow.json`), `style` (the video's `style.primary`), `voice` (its `voiceUsed`), `geo` and `flowSha` from `pipeline2/videos/vN.json`, so posts can be compared by style, voice and audience later.
4. On failure (render, fact check or upload twice): release with `"set":{"status":"approved","note":"<why>"}` only if it is worth another try, else `"status":"rejected"`, and write why into `note`. Go back to step 1. Stop after `build.maxPerRun` videos or two failures.

5. After the builds (or when nothing was approved), make missing platform versions for videos already approved, as in "Platform versions for the queue", up to `build.maxVersionsPerRun`.

This run never proposes new ideas or stories; that is the scout's job.

6. Last, draft comment replies as in "Comment replies" below.

Final reply: one line per video (item id, type, file, duration, verification result, slot for news), and "nothing approved" when step 1 found nothing.

Alert: when the run made 0 videos although step 1 found approved cards, or it stopped after two failures or on the time budget with cards left, send one alert before the final reply: `inbox.sh call '{"action":"add","id":"alert-build-<YYYY-MM-DD>","type":"todo","status":"pending","title":"Build run: <n> videos made, <why>","summary":"<each failed card id and its note>","data":{"app":"How To Hero","icon":"🚨"}}'`. Telegram sends it as a message. Failed posts already alert from the Inbox (red FAILED message), and the publisher alerts when a video is more than 3 hours past its slot.

## Worker steps

Make exactly the claimed item, using "Build one video" below. Length cap: `data.maxSeconds`, else by `series` (A 120, B 120, C 150, D 120), else 60. Skip any item whose `series` is "DOC" or `kind` is "doc" (see "Documentaries"). Fact check: if `fact` is K (to check), look up a named source for every number and date before writing; if you cannot, release the item as a failure (step 4) with the reason in `note`. If `fact` is C (contested), the narration says "scientists think" and names the evidence. Then fill these `data` fields for the hand-in:
- `videoRef` = `<file> | <duration> s | ffprobe: 1080x1920, 30 fps, H.264 yuv420p + AAC stereo 48 kHz, <MB> MB | audio peak <dB> dB | safe zone: <n> violations`.
- Publish kit: `yt` = the title, at most 70 characters, the claim first and the searchable noun in it ("India Had Its Own Horned Killer Dinosaur: Rajasaurus"), no "in 60 Seconds", ending in ` #shorts`; `ig` = first line holds the topic keywords, second line one extra fact, then `Sources: <names>`, then `Follow @howtohero.official` and 3 to 5 specific hashtags (never #reels, #explore, #viral); `pin` = one specific question the video raises, for the pinned comment. The auto-publisher uses these as captions. Also write `meta` = `{"youtube": {"title", "text"}, "instagram": {"text"}, "facebook": {"title", "text"}}`, each written to the `metadata` rules in that platform's `platforms/<platform>.json`; the publisher posts `meta.<platform>` and falls back to `yt`/`ig` when it is missing. Same video everywhere, only the words change.
- Never touch other items.

## Build one video (id vN: one more than the highest vN in `pipeline2/videos/` and `pipeline/videos/`; v18 was the first pipeline2 idea video)

Shorts are made with `pipeline2/` (canvas renderer, 5 code-drawn styles, see `pipeline2/README.md` for the scene format). Its settings (styles, voices) come from `flow.json`; never pick a style or voice by hand unless the card's `note` asks for one. Documentaries still use the old `pipeline/` ("Documentaries" below). Work in the repo's `pipeline2/` folder; `work/` and voice files are ignored by git.

1. `cd <skill dir>/pipeline2`. The Kokoro voice needs `hyperframes` available to `npx` (as before); the Indian English voice needs the `edge-tts` Python package and the network, and falls back to Kokoro by itself when either is missing. In a fresh cloud container, first run `pip install kokoro-onnx soundfile edge-tts` and `export HYPERFRAMES_PYTHON=/usr/bin/python3`, and run `verify.py` with `python3.13` if the default `python3` fails to import PIL (seen 18 Nov).
2. Write `pipeline2/videos/vN.json` (worked examples: `pipeline2/videos/n-quake.json`, `n-hubble.json`): `file` = `how-<topic>-works.mp4`, a 2-line `hook` (≤ 22 chars/line, ONE yellow word), `topic` (the subject in 1-3 words), `maxSeconds` (the cap above), `geo` (copy the card's `data.geo`, else `global`), `beats` (`say` lines) and `card` lines. Rules that decide whether a viewer stays (63% of our first viewers swiped away, so these are not optional):
   - Hook: a surprising claim or a contradiction ("GPS NEVER SENDS ANYTHING"), never a question and never the topic restated. Test: cover the topic label; the hook must still say something a viewer did not know.
   - First spoken line: the same claim, in at most 12 words. Background and dates come after it.
   - Length: as long as the story needs and no longer. Do not set `target` (it stretches the voice to 58 s); a 60 s cap usually means 7-9 spoken beats and 40-50 s. About 2.6 words per second with Kokoro, about 2.2 with Neerja (India cards), so an India card needs about 20% fewer words.
   - Ending: the last spoken line is the payoff, ideally something the viewer would repeat to a friend. No spoken "follow" line. The final beat is the silent end card: `{ "hold": 1.6 }` with `card` lines `["FOLLOW FOR MORE", "HOW TO HERO"]` (the `n-*` news examples use a longer news end card; for ideas follow this rule, as `pipeline2/videos/v18.json` does). A card with no `data.kind` is an `explainer`.
   Plain present or past tense. Accurate and conceptual: invent no numbers, show no real logos/brands.
   Then get a second opinion before drawing anything: write the hook, every spoken beat, the end card and the sources (with the facts each one backs) to `work/vN.review.txt` and run `python3 <skill dir>/advisor.py script work/vN.review.txt` (see "Advisor"). Apply every FACTS fix; take the HOOK and SCRIPT fixes unless they break a rule above. On STOP, treat it as a failed fact check (build run step 4).
3. Write `pipeline2/videos/vN.scenes.json`: one entry per spoken beat with an `intent`, a `shot` (camera, framing, subject, action) and its `items`, as in `pipeline2/README.md` "Scene rules". Beat 1 is on screen from frame 0 and something moves in the first second. Keep at most 3 moving shots per video. Then `node flow.mjs resolve videos/vN.json` (writes `style` and `flowSha` once; a card `note` naming a style wins) and `node schema.mjs videos/vN.json` (0 errors).
4. `node build.mjs videos/vN.json` (makes the voice with the video's voice from `flow.json`: India cards get Neerja, the rest Kokoro; it records `voiceUsed`), then `node render.cjs work/vN/page.json work/vN/stills --frames 0.5,<the middle of each beat>,<0.45 s before each beat ends>` and look at every still for clipped, overlapping or empty drawings: mid-beat catches layout, the late still shows the finished labels (text types on slowly, and blueprint slides between beats in the last 0.35 s). Fix the scenes and rebuild; a rebuild reuses the voice clips when the words and voice are unchanged.
5. `node render.cjs work/vN/page.json ../out/<file>` (about 3 minutes; run one render at a time), then `python3 verify.py work/vN/page.json ../out/<file> --max <maxSeconds>` and `python3 sheet.py work/vN/page.json ../out/<file>`. Every line must be `ok`. If a check fails, reshoot once: read the failing line, change the shots or items that cause it in `vN.scenes.json` (or shorten the lines when it is the length), rebuild, render and verify again. A second failure is a build failure (build run step 4) with the failing line in `note`. Also save `../out/vN.cover.png` (the frame at 0.5 s) and check the hook is readable in it.

## Platform versions

Each platform we post to has one file, `platforms/<platform>.json` (repo root): the single source of truth for that platform. Read every one before planning a video. When the finished video is longer than a platform's `maxSeconds`, make a separate version for that platform; never post or upload a truncated copy.
1. Make id `vN-<platform>`: copy `pipeline2/videos/vN.json` to `pipeline2/videos/vN-<platform>.json` with `file` = `<file stem>-<platform>.mp4` and `maxSeconds` = the platform's `versionSeconds` (keep `style` and `voice` so the version looks and sounds the same), and copy `vN.scenes.json` to `vN-<platform>.scenes.json` keeping one scene entry per kept line. Old videos built with `pipeline/` keep using `videos/vN.json` + `vN.scenes.js` there. Keep the hook, the topic label and the end card; keep the beats that carry the key idea and the payoff, and drop or merge the rest (about 2.6 words per second, so 39 s is about 85 spoken words). It must stand alone: no "part 1", no cliffhanger.
2. Build, render and verify it exactly as in "Build one video" steps 4-5 with id `vN-<platform>` (verify.py reads its `maxSeconds`, and `versionSeconds` plus verify's 2 s margin stays under the platform's limit).
3. `inbox.sh upload out/<file stem>-<platform>.mp4 <item id>` prints the Drive file id. Put it in `data.versions` as `{"<platform>": "<file id>"}` (keep any other platforms already there). Also set `data.links` so the Inbox card and Telegram show every version: `{"Main": "<item link>", "<Platform>": "https://drive.google.com/file/d/<file id>/view"}`, one entry per version (the publisher also fills these in on each run).
The publisher posts a platform only from the main video (when it fits) or from its version; a platform without either is skipped with a yellow "needs its own version" chip.

### Platform versions for the queue

Approved videos built before versions existed may lack one. List `{"action":"list","type":"video","status":"approved","limit":1000}`, order them as the publisher does (news first, then by `slot`), and take the first ones whose length (in `videoRef`, `| 47.3 s |`) is over a platform's `maxSeconds` and which have no `data.versions.<platform>`. For each: use its `videos/vN.json` when it exists (the `file` in `videoRef` names it), else write one from the item's `title`, `summary`, `data` (`topic`, `ig`, `sources`) and the main video's narration; build the version as above; then save it with `get` and `update` (`"ifVersion"`, `"set":{"data":{<the item's data plus versions and links>}}`). Do not change the item's status.

## Advisor (second opinion from a stronger model)

At two decisions, the jobs ask a stronger model to check their work: the scout's cards before they reach the user (`SCOUT.md`), and each script before render ("Build one video" step 2). Nowhere else: each call costs real money.

`advisor.py <cards|script> <file>` sends the file to Claude Fable 5.2 through the API (paid from the user's API credits; key in the environment variable `HTH_ADVISOR_KEY`, never printed) and prints its advice plus the cost of the call. It stops spending by itself: after `HTH_ADVISOR_RUN_BUDGET` dollars in one run (default 2.00), or when the key is missing or refused, or the credits are used up.

Exit code 3 means no advice; the first line says `FALLBACK: <reason>`. Then get the same second opinion in-session: start one subagent with the Agent tool, `model: "fable"`, and give it the text that `advisor.py <task> <file> --prompt` prints. If no subagent can be started, review the file yourself once more against that prompt, as a strict editor who did not write it. Never skip the review, and never stop the run because the advisor is unavailable. Put each call's cost line (or the fallback reason) in the final reply.

## Comment replies (scout and build runs, last step)

The publish workflow (`publisher/replies.py`) turns each new viewer comment on YouTube, Instagram or Facebook (`data.platform`) into an Inbox item of type `reply` in status `building`, and posts the replies the user approves. These runs only write the drafts. List them: `inbox.sh call '{"action":"list","type":"reply","status":"building","limit":50}'`. For each:
- Spam, follow-for-follow, self-promotion or abuse with no question in it: `"set":{"status":"rejected","note":"no reply: <why>"}`.
- Links in Instagram replies aren't clickable, so there name the source instead of linking it.
- Otherwise write the reply the way a friendly person on the team would: 1 to 3 short sentences, casual, never defensive or corporate, no hashtags. Agree with what's fair in the comment first ("Ha, fair, it sounds wrong at first!"), then answer with one concrete fact. When the comment questions a fact, check it and end with one reliable source link (a mission page, agency or paper, not a random blog), introduced in a few words. Thanks plus a hint at what's coming is enough for plain praise. An emoji at most. If the comment is right and the video is wrong, say so plainly and thank them.
- Tag the comment as `question` (asks how or why), `correction` (says a fact in the video is wrong), `idea` (asks for a topic) or `other`, and save the tag as `data.tag`. For a `correction` you checked and found right, also add an alert to-do: `inbox.sh call '{"action":"add","id":"alert-fix-<reply item id>","type":"todo","status":"pending","title":"Viewer found a mistake in <video title>","summary":"<the comment>, <what is wrong and the source>. Pin a correction or pull the video.","data":{"app":"How To Hero","icon":"🚨"}}'`. The scout reads `question` and `idea` tags for new cards.
- Save it with `"set":{"status":"pending","data":{...the existing data, "tag":"<tag>", "reply":"<the reply>"},"summary":"💬 <author>: <comment>\n\n↩️ Draft reply: <the reply>"}`. Pending sends it to Telegram. The user approves it as is, or writes the edited text as the approval note, which gets posted instead.

Never post a reply yourself. Put the count in the final reply: drafted, skipped as spam.

## Rules

Old pipeline only (documentaries, old ids): brand navy 1F2A6B, yellow FFC531, red E5384F, white, Anton caps, dark navy gradient, progress bar at bottom edge, stick-man hero end card. Safe zone: all key content inside x 60-940, y 420-1500 (pipeline2 uses x 60-940, y 200-1360 for drawings, with the hook and captions placed by its brand layer); headline ≥ 90 px; captions ≥ 56 px, ≤ 2 lines around y 1250-1450. Hook text on screen in the first 2 s. Known pitfalls: never `gsap.set(opacity)` on elements later driven by `setAttribute`; use `fadeTo` for translucent elements; end-card text is 72 px (known deviation, mention it).

## Documentaries (16:9, long form)

Items with `series` = "DOC" are YouTube documentaries, not shorts. The build run must skip them (also skip any id that starts with `doc-`). To build one, set `"format": "doc"` in `videos/dN.json` (ids `d1`, `d2`, ...): `build.mjs` then makes a 1920x1080 frame, lifts the 62 s cap to `maxSeconds` (default 360), and `verify.py` checks 1920x1080, a < 500 MB file and the 16:9 safe zone (x 100-1820, y 50-1040, sampled once a second). Scenes draw in a 1680x780 box (frame offset 120,70); captions sit below it; beat 0 stays empty under the headline; the last beat is the "Subscribe for more" mascot card. About 2.6 words per second; an 8-minute doc is about 1,250 words in 55-75 beats, with chapter title cards. Rendering runs at about 2.6x real time on 4 cores, so an 8-minute doc takes about 20 minutes; run renders one at a time (`flock` a lock file when several agents share the machine).
